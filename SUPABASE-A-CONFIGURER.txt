Sensorielle — ce qu'il reste à configurer dans Supabase
=========================================================

Ce fichier n'est pas nécessaire sur ton hébergement (comme LIRE-MOI.txt) —
garde-le juste pour toi, comme liste de choses à faire dans le tableau de
bord Supabase (https://supabase.com/dashboard). Je n'ai pas accès à ce
tableau de bord depuis ici, donc tout ce qui suit doit être fait par toi,
à la main, une seule fois.

Projet concerné : frinlluqjbwgctkzqoea (déjà utilisé pour les comptes).


1) Table + bucket pour "Contribuer un signe" (collector/index.html)
--------------------------------------------------------------------

a. Storage > New bucket
   - Nom : contributions
   - Public : non nécessaire (peut rester privé)

b. Storage > contributions > Policies > New policy
   - Autoriser INSERT pour le rôle "anon" (ou "authenticated" si tu
     préfères forcer la connexion avant de contribuer — actuellement le
     formulaire n'exige pas de compte).

c. Table editor > New table
   - Nom : contributions
   - Colonnes :
       id          uuid       clé primaire, défaut gen_random_uuid()
       word        text       NOT NULL
       note        text       NULLABLE
       email       text       NULLABLE
       video_path  text       NOT NULL   (chemin dans le bucket "contributions")
       status      text       défaut 'pending'
       created_at  timestamptz défaut now()

d. Active "Row Level Security" sur cette table, puis ajoute une policy
   qui autorise INSERT pour "anon" (même principe qu'en b).

   Pour réviser les contributions reçues : Table editor > contributions,
   et pour écouter/voir la vidéo associée, Storage > contributions >
   cherche le fichier par son "video_path". Pas besoin d'un panneau
   d'administration séparé pour l'instant — l'éditeur de tables de
   Supabase suffit pour approuver ou rejeter à la main.

3) Ce qui est DÉJÀ en place (rien à faire)
---------------------------------------------

- Les comptes (courriel/mot de passe, connexion Google, photo de profil)
  utilisent déjà Supabase Auth — aucune nouvelle table n'est nécessaire
  pour ça, c'est géré automatiquement.


4) Rappel sécurité, en une phrase
------------------------------------

Chaque nouvelle table doit avoir RLS activée avec UNIQUEMENT les
politiques dont tu as besoin (ici : INSERT pour "anon") — jamais une
politique "allow all" qui permettrait aussi de LIRE ou MODIFIER les
soumissions des autres personnes.


Tant que ces tables/bucket n'existent pas, les deux formulaires
concernés (Contribuer un signe, Demander une démo) échouent proprement
et proposent automatiquement un envoi par courriel à la place — rien
n'est perdu en attendant.


5) Tableau de bord admin (dashboard/index.html, code 2244)
---------------------------------------------------------------

Permet de voir, pour chaque compte, le journal de ses phrases traduites
(date, heure, texte, signes affichés) - utile pour verifier que la
traduction fonctionne bien en vrai, phrase par phrase.

a. Supabase > SQL Editor > New query > colle TOUT le bloc SQL ci-dessous
   > Run. Ca cree les tables "profiles" et "conversation_logs", remplit
   profiles pour les comptes existants, et met en place les regles de
   securite (RLS) - PERSONNE ne peut lire les conversations de quelqu'un
   d'autre, sauf un compte explicitement marque admin (etape b).

   -- debut du bloc a copier --

   create table if not exists public.profiles (
     id uuid primary key references auth.users(id) on delete cascade,
     email text,
     created_at timestamptz not null default now(),
     is_admin boolean not null default false
   );

   create table if not exists public.conversation_logs (
     id bigint generated always as identity primary key,
     user_id uuid not null references auth.users(id) on delete cascade,
     text text not null,
     signs text[],
     created_at timestamptz not null default now()
   );

   create index if not exists conversation_logs_user_created_idx
     on public.conversation_logs (user_id, created_at desc);

   create or replace function public.handle_new_user()
   returns trigger
   language plpgsql
   security definer
   set search_path = public
   as $$
   begin
     insert into public.profiles (id, email)
     values (new.id, new.email)
     on conflict (id) do nothing;
     return new;
   end;
   $$;

   drop trigger if exists on_auth_user_created on auth.users;
   create trigger on_auth_user_created
     after insert on auth.users
     for each row execute function public.handle_new_user();

   insert into public.profiles (id, email, created_at)
   select id, email, created_at from auth.users
   on conflict (id) do nothing;

   create or replace function public.is_admin()
   returns boolean
   language sql
   security definer
   set search_path = public
   stable
   as $$
     select coalesce((select is_admin from public.profiles where id = auth.uid()), false);
   $$;

   alter table public.profiles enable row level security;
   alter table public.conversation_logs enable row level security;

   drop policy if exists "profiles: lecture propre ou admin" on public.profiles;
   create policy "profiles: lecture propre ou admin"
     on public.profiles for select
     using (auth.uid() = id or public.is_admin());

   drop policy if exists "logs: ajout de ses propres lignes" on public.conversation_logs;
   create policy "logs: ajout de ses propres lignes"
     on public.conversation_logs for insert
     with check (auth.uid() = user_id);

   drop policy if exists "logs: lecture propre ou admin" on public.conversation_logs;
   create policy "logs: lecture propre ou admin"
     on public.conversation_logs for select
     using (auth.uid() = user_id or public.is_admin());

   -- fin du bloc a copier --

b. ENSUITE, dans une NOUVELLE requete SQL Editor, remplace l'adresse par
   TON courriel de connexion sur Sensorielle (celui que tu tapes dans la
   fenetre "Se connecter" du site, pas necessairement ton Gmail), et
   execute SEULEMENT cette ligne :

   update public.profiles set is_admin = true where email = 'TON_COURRIEL_ICI';

   C'est CETTE ligne qui decide qui peut voir les conversations de tout
   le monde dans le tableau de bord - pas le code 2244 de la page (qui
   n'est qu'un verrou simple, comme un code de porte, pas une vraie
   securite). Sans etre a la fois (1) connecte sur le site avec CE
   compte admin ET (2) sur la page /dashboard/, personne - meme en
   connaissant le code 2244 - ne peut lire les conversations des autres.

c. Important : connecte-toi sur sensorielle.ca avec ce compte admin
   AVANT d'ouvrir /dashboard/ - le tableau de bord réutilise la session
   déjà ouverte sur le site, il ne redemande pas de mot de passe.
